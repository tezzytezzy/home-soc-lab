# DNS and Network Configuration Baseline

## Overview

During the setup of the Home SOC lab, I initially attempted to use:

```bash
resolvectl status
```

to inspect the system's DNS configuration.

The command was not available:

```text
Command 'resolvectl' not found, but can be installed with:
sudo apt install systemd-resolved
```

Rather than immediately installing `systemd-resolved`, I investigated how DNS was already configured on the system.

This was an intentional decision.

A security lab should avoid making unnecessary changes to a working operating system. Before installing a new system component, I wanted to determine whether the component was actually required.

The investigation showed that Kali Linux 2026.2 on this system is using **NetworkManager to manage networking and DNS**, so `systemd-resolved` is not required for the Home SOC project.

---

# Why This Investigation Was Necessary

The Home SOC project needs basic network information such as:

* Network interface
* IP address
* Default gateway
* DNS configuration
* Listening services
* Active connections

Initially, I planned to use:

```bash
resolvectl status
```

to obtain DNS information.

However, `resolvectl` is associated with `systemd-resolved`.

The absence of `resolvectl` does **not** necessarily indicate a problem.

It may simply mean that the system is using another DNS-management mechanism.

Therefore, instead of changing the system, I first investigated the existing configuration.

The principle followed was:

> **Observe the existing system before modifying it.**

---

# Initial Observation

Running:

```bash
resolvectl status
```

produced:

```text
Command 'resolvectl' not found, but can be installed with:
sudo apt install systemd-resolved
```

At first glance, installing `systemd-resolved` might appear to be the obvious solution.

However, installing a package because a command is missing does not necessarily mean that the package is needed.

Before making any changes, I checked the current networking configuration.

---

# Step 1 — Inspect `/etc/resolv.conf`

I ran:

```bash
ls -l /etc/resolv.conf
```

The result was:

```text
-rw-r--r-- 1 root root 50 Sep 27 17:54 /etc/resolv.conf
```

This showed that `/etc/resolv.conf` is a regular file rather than a symbolic link.

I then inspected its contents:

```bash
cat /etc/resolv.conf
```

The result was:

```text
# Generated by NetworkManager
nameserver 11.0.0.1
```

## Interpretation

The most important piece of information is:

```text
# Generated by NetworkManager
```

This indicates that NetworkManager is responsible for generating the current resolver configuration.

The configured DNS server is:

```text
11.0.0.1
```

For security and privacy reasons, actual network-specific information should not be published in this repository.

In public documentation, network-specific information should be sanitized or replaced with placeholders such as:

```text
<LOCAL_DNS_SERVER>
```

---

# Step 2 — Check Which Network Services Are Running

I then checked for NetworkManager and `systemd-resolved` processes:

```bash
ps aux | grep -E '[r]esolved|[N]etworkManager'
```

The result showed:

```text
root 634 ... /usr/sbin/NetworkManager --no-daemon
```

There was no `systemd-resolved` process.

This provided additional evidence that NetworkManager, rather than `systemd-resolved`, is managing the system's network configuration.

---

# Step 3 — Check NetworkManager's Service Status

I ran:

```bash
systemctl status NetworkManager --no-pager
```

NetworkManager reported:

```text
NetworkManager.service - Network Manager
Loaded: loaded
Active: active (running)
```

The service also reported that the wireless interface had successfully obtained a DHCP lease and that NetworkManager had configured DNS.

The important observations were:

```text
NetworkManager: active (running)
wlan0: DHCP lease obtained
NetworkManager: DNS configured
NetworkManager: connected
```

This confirmed that the existing network configuration was functioning normally.

---

# Step 4 — Check Overall Network Connectivity

I then ran:

```bash
nmcli general status
```

The result was:

```text
STATE      CONNECTIVITY  WIFI-HW  WIFI     WWAN-HW  WWAN     METERED
connected  full          enabled  enabled  missing  enabled  no (guessed)
```

The important fields were:

```text
STATE:        connected
CONNECTIVITY: full
WIFI:         enabled
```

This confirmed that the system had working network connectivity.

---

# Step 5 — Consider Installing `systemd-resolved`

Because `resolvectl` was unavailable, I checked what would happen if `systemd-resolved` were installed.

I first simulated the installation:

```bash
sudo apt install --simulate systemd-resolved
```

APT reported:

```text
Installing:
  systemd-resolved

Summary:
  Upgrading: 0
  Installing: 1
  Removing: 0
  Not Upgrading: 1194
```

The transaction did not propose removing or upgrading existing packages.

However, this did **not** mean that installing `systemd-resolved` was necessary.

There is an important distinction:

> **A package can be safe to install from APT's dependency perspective without being necessary for the system's current architecture.**

The Home SOC project only requires DNS visibility and network telemetry. It does not require changing the system's DNS resolver architecture.

Therefore, I decided **not to install `systemd-resolved`**.

---

# Current Network Architecture

The investigation established the following architecture:

```text
                    Network
                       │
                       │
                     wlan0
                       │
              ┌────────▼────────┐
              │  NetworkManager │
              └────────┬────────┘
                       │
                 DHCP configuration
                       │
              ┌────────▼────────┐
              │ /etc/resolv.conf│
              └────────┬────────┘
                       │
                  DNS Server
```

The important point is that the system is using **NetworkManager-managed DNS configuration**.

`systemd-resolved` is not required for this architecture.

---

# Decision

## Do not install `systemd-resolved`

The decision was based on the following observations:

1. NetworkManager is active.
2. NetworkManager successfully configured the wireless interface.
3. NetworkManager generated `/etc/resolv.conf`.
4. DNS configuration is already present.
5. Network connectivity is working.
6. `systemd-resolved` is not currently running.
7. The Home SOC project does not require `systemd-resolved`.

Therefore, installing `systemd-resolved` would introduce a new system component without providing a requirement that the project currently needs.

---

# Corrected Home SOC Baseline Procedure

The original plan included:

```bash
resolvectl status
```

This has been removed from the baseline procedure.

Instead, network and DNS information can be collected using tools already appropriate for this Kali configuration.

## Network interfaces

```bash
ip addr
```

### Purpose

Shows:

* Network interfaces
* IP addresses
* Interface state
* MAC addresses

---

## Routing

```bash
ip route
```

### Purpose

Shows:

* Default gateway
* Network routes
* Interface used for routing

---

## NetworkManager configuration

```bash
nmcli device show wlan0
```

### Purpose

Provides detailed NetworkManager information for the wireless interface.

For DNS information specifically:

```bash
nmcli device show wlan0 | grep -i DNS
```

---

## Current resolver configuration

```bash
cat /etc/resolv.conf
```

### Purpose

Shows the DNS resolver configuration currently being used by applications through the standard resolver configuration file.

---

## Listening services

```bash
ss -tulpen
```

### Purpose

Identifies services listening for network connections.

This is important for the Home SOC baseline because it establishes what services are expected to be exposed by the system.

---

## Active TCP connections

```bash
ss -tp
```

### Purpose

Shows active TCP connections.

This provides a baseline for understanding normal network activity before beginning traffic analysis.

---

# Why This Matters for the Home SOC

The purpose of the baseline is not to install every available security or networking utility.

The purpose is to understand the system being monitored.

The investigation follows:

```text
Observe
   ↓
Understand
   ↓
Document
   ↓
Change only when necessary
```

rather than:

```text
Missing command
   ↓
Install package
   ↓
Change system
   ↓
Hope nothing breaks
```

This is particularly important because the Home SOC environment already contains security tooling such as Zeek and Suricata.

Unnecessary system modifications could introduce dependency or configuration problems that have nothing to do with the actual security objective.

---

# Lessons Learned

## 1. A missing command does not necessarily indicate a broken system

`resolvectl` was unavailable, but DNS and networking were functioning correctly.

The missing command reflected the system's networking architecture rather than a failure.

---

## 2. Identify the component responsible for a function

Before installing `systemd-resolved`, I determined that NetworkManager was already managing DNS.

This avoided introducing a second DNS-management component unnecessarily.

---

## 3. Simulate package changes before applying them

The command:

```bash
sudo apt install --simulate systemd-resolved
```

was useful because it showed what APT intended to change without actually modifying the system.

This is especially useful on a security lab where package dependencies need to be treated carefully.

---

## 4. A clean package transaction does not automatically mean installation is necessary

APT reported:

```text
Upgrading: 0
Installing: 1
Removing: 0
```

That indicated a clean package transaction.

However, the package still wasn't required for the project's objectives.

This distinction is important:

> **Package safety and architectural necessity are separate questions.**

---

## 5. Security monitoring begins with understanding the environment

Before monitoring network traffic, it is useful to understand:

```text
What interface am I using?
What IP address do I have?
What is my default gateway?
Who manages DNS?
What DNS server am I using?
What services are listening?
What connections are currently active?
```

These questions establish the baseline needed to recognize unusual activity later.
