# IP Address and NAT Observation

## Overview

While establishing the network baseline for my Home SOC lab, I noticed an apparent discrepancy between the IP address assigned to my laptop's wireless interface and the IPv4 address reported by an external "what is my IP" website.

The laptop reported an address similar to:

```text
11.0.30.232
```

while an external Internet service reported a different address:

```text
<PUBLIC_IP>
```

When I used the laptop's interface address as a Wireshark filter, traffic appeared:

```text
ip.addr == <LOCAL_INTERFACE_IP>
```

When I used the externally observed address:

```text
ip.addr == <PUBLIC_IP>
```

no packets appeared.

This initially appeared confusing, but it is consistent with the difference between an address assigned to a local network interface and an address observed by an external Internet service.

This investigation helped establish an important networking concept for the Home SOC project:

> **The IP address assigned to a network interface is not necessarily the same IP address that external Internet services observe.**

---

# 1. Initial Observation

An external Internet service reported an IPv4 address:

```text
<PUBLIC_IP>
```

This address was described as the IPv4 address assigned by the ISP.

However, inspecting the laptop's network interface showed:

```text
3: wlan0: <BROADCAST,MULTICAST,UP,LOWER_UP>
    mtu 1500
    state UP
    group default
    qlen 1000

    link/ether <SANITIZED_MAC>
    brd <SANITIZED_BROADCAST_MAC>

    inet <LOCAL_INTERFACE_IP>/18
    brd <SANITIZED_BROADCAST_ADDRESS>
    scope global dynamic
    noprefixroute
    wlan0
```

The important observation was:

```text
wlan0
└── <LOCAL_INTERFACE_IP>
```

This is the address currently assigned to the laptop's wireless interface.

---

# 2. Why Two Different IP Addresses Exist

The network can be represented conceptually as:

```text
                    INTERNET
                        │
                        │
                <PUBLIC_IP>
                        │
                 ┌──────▼──────┐
                 │   Gateway   │
                 │ / NAT layer │
                 └──────┬──────┘
                        │
                  Local Network
                        │
                        │
              <LOCAL_INTERFACE_IP>
                        │
                 ┌──────▼──────┐
                 │    Laptop   │
                 │    wlan0    │
                 └─────────────┘
```

The laptop's network interface exists on the local side of the network.

An external website exists on the Internet side.

Therefore, the two systems can observe different IP addresses for the same communication.


# 7. Wireshark Observation

I then investigated the difference using Wireshark.

When the following display filter was applied:

```text
ip.addr == <LOCAL_INTERFACE_IP>
```

packets associated with the laptop appeared.

This was expected because `<LOCAL_INTERFACE_IP>` is assigned directly to the laptop's `wlan0` interface.

Conceptually:

```text
Laptop
  │
  └── wlan0
       └── <LOCAL_INTERFACE_IP>
```

Wireshark is observing traffic at this interface.

---

# 8. Testing the Public IP Address

I then used the externally observed address as a Wireshark filter:

```text
ip.addr == <PUBLIC_IP>
```

No packets appeared.

Initially this seemed contradictory.

However, Wireshark's filter:

```text
ip.addr == <PUBLIC_IP>
```

means:

> Display packets where `<PUBLIC_IP>` is either the source or destination IPv4 address.

The laptop's wireless interface does not necessarily see the Internet-facing packet after it has passed through the upstream gateway/NAT infrastructure.

Therefore, the absence of packets matching `<PUBLIC_IP>` does not indicate that the external IP address is incorrect.

---

# 9. NAT and Address Translation

A simplified outbound connection can be represented as:

```text
BEFORE ADDRESS TRANSLATION

Source:
<LOCAL_INTERFACE_IP>:<EPHEMERAL_PORT>

Destination:
<REMOTE_SERVER_IP>:443
```

The packet travels toward the network gateway.

The gateway may perform address translation:

```text
<LOCAL_INTERFACE_IP>:<EPHEMERAL_PORT>
                    │
                    ▼
                  NAT
                    │
                    ▼
<PUBLIC_IP>:<TRANSLATED_PORT>
```

The Internet-facing connection can therefore appear externally as originating from `<PUBLIC_IP>`.

The remote server sees the externally routable address rather than necessarily seeing the address assigned to the laptop's local interface.

---

# 10. Important Qualification

The external IP address reported by a website demonstrates the address that the website observed for the Internet connection.

It does **not, by itself, prove that the laptop's immediate Wi-Fi gateway directly owns that public address**.

There may be additional network infrastructure between the laptop and the public Internet.

For example:

```text
Laptop
   │
   │ <LOCAL_INTERFACE_IP>
   ▼
Local Gateway
   │
   ▼
Additional Network / ISP Infrastructure
   │
   │ <PUBLIC_IP>
   ▼
Internet
   │
   ▼
External Website
```

Therefore, this project does not assume the exact location where address translation occurs without additional evidence.

The technically precise statement is:

> **An external Internet service observed `<PUBLIC_IP>` as the public source address associated with the connection.**

---

# 11. Why the Wireshark Filters Behave Differently

The two filters are asking Wireshark different questions.

### Filter 1

```text
ip.addr == <LOCAL_INTERFACE_IP>
```

Question:

> "Show me packets involving the IP address assigned to my laptop's network interface."

Result:

```text
Packets appear
```

This is expected.

---

### Filter 2

```text
ip.addr == <PUBLIC_IP>
```

Question:

> "Show me packets involving the public address observed externally."

Result:

```text
No packets observed
```

This is also expected if the address translation occurs beyond the interface being monitored.

---

# 12. Why This Matters for Security Monitoring

This observation is important for the Home SOC because IP addresses need context.

Suppose a security alert contains:

```text
Source IP: <LOCAL_INTERFACE_IP>
```

That may indicate traffic originating from the monitored laptop itself.

However, an external system may see:

```text
Source IP: <PUBLIC_IP>
```

for traffic originating from the same Internet connection.

Therefore, an analyst should understand:

```text
Local IP
   ↓
Local network
   ↓
Gateway / NAT
   ↓
Public IP
   ↓
Internet
```

before interpreting an IP address in isolation.

---

# 13. Security Investigation Principle

This investigation reinforced an important principle:

> **An IP address has meaning only in the context of where it was observed.**

An address observed on:

```text
wlan0
```

is different from an address observed by:

```text
an Internet server
```

even when both are associated with the same communication.

For SOC investigations, useful contextual information includes:

* Source IP
* Destination IP
* Source port
* Destination port
* Network interface
* Timestamp
* Protocol
* Routing information
* NAT boundaries
* DNS information

# 14. Useful Commands for the Network Baseline

The following commands can be used to establish the local network baseline.

## Interfaces

```bash
ip addr
```

Purpose:

* Identify interfaces
* Identify assigned IP addresses
* Determine interface state

---

## Routing

```bash
ip route
```

Purpose:

* Identify the default route
* Identify the local gateway
* Determine which interface handles outbound traffic

---

## NetworkManager

```bash
nmcli device show wlan0
```

Purpose:

* Inspect NetworkManager's configuration for the wireless interface.

For DNS information:

```bash
nmcli device show wlan0 | grep -i DNS
```

---

## Resolver configuration

```bash
cat /etc/resolv.conf
```

Purpose:

* Inspect the resolver configuration currently provided to the system.

---

## Listening services

```bash
ss -tulpen
```

Purpose:

* Establish a baseline of services listening on the machine.

---

## Active connections

```bash
ss -tp
```

Purpose:

* Identify active TCP connections.

# 16. Lessons Learned

### Lesson 1 — Local and public addresses are different concepts

The address assigned to a network interface is not necessarily the address observed by an external Internet service.

### Lesson 2 — Wireshark sees traffic at a particular observation point

A packet capture taken on the laptop's wireless interface shows what is visible at that interface.

It does not automatically show every transformation that occurs farther upstream.

### Lesson 3 — NAT changes the apparent source address

A gateway or upstream network device can translate an internal source address into an externally visible address.

### Lesson 4 — Do not infer network architecture from a single IP address

The public IP reported by an external website tells me what that website observed.

It does not, by itself, identify which specific network device performed the translation.

### Lesson 5 — Security analysts need network context

When investigating an IP address, I should consider:

```text
Where was it observed?
When was it observed?
On which interface?
Was NAT involved?
What was the destination?
What protocol was used?
```

---

# Conclusion

The apparent discrepancy between the IP address assigned to `wlan0` and the address reported by an external IP-checking service is not necessarily a contradiction.

They represent observations made at different points in the network.

The Home SOC lab can therefore be visualized as:

```text
                   INTERNET
                       │
                       │
                <PUBLIC_IP>
                       │
               Network Boundary
                 / NAT Layer
                       │
                       │
              <LOCAL_INTERFACE_IP>
                       │
                    wlan0
                       │
                    Kali
                       │
          ┌────────────┼────────────┐
          │            │            │
      Wireshark       Zeek       Suricata
```

This distinction will be important when correlating Wireshark captures, Zeek logs, and Suricata alerts later in the Home SOC project.

The key takeaway is:

> **Always interpret an IP address according to where and how it was observed.**
